Shabbat, calendar & reminders architecture

A Calendar Service handles all the calendar calculations. A Reminders Service decides when to notify you and publishes to Kafka. A Notification Service decides how (push today, and email or SMS later with one new adapter each).

System

Phase 1: Shabbat + Calendar tab Phase 2: reminders + notifications future channels internal Docker network (only Gateway published)

The three services

Phase 1

Calendar Service

Every calendar calculation, in one place.

  • Next Shabbat, month grid, holidays, fasts, daily times
  • Stateless: location in, times out. No database.
  • Used by the phone (via Gateway) and by Reminders
Phase 2

Reminders Service

What to remind you about, and when.

  • Every reminder belongs to one user and needs you to be logged in
  • First type: before candle lighting, with the offset you pick (e.g. 1h 30m), repeating every week
  • Later: other types (before a holiday, custom date/time) reuse the same table
  • When a reminder is due it publishes an event and stops there. It never knows about push, email or SMS.
Phase 2

Notification Service

How to reach you.

  • Consumes notification.requested from Kafka
  • Knows your push tokens (later: email address, phone number)
  • One adapter per channel behind INotificationChannel. Email or SMS is a new adapter, with no change to Reminders.
  • Any future service can send you a notification the same way

Where it lives: a bell button on the Shabbat section of the Home card (H1). Tapping it opens a sheet with an hours/minutes picker and quick presets. The button label shows what's set. It's per user, so if you're signed out, tapping it shows the same "log in to use this" prompt the Account tab uses.

What gets saved: one row per user and type, not one per week.

-- reminders
id            uuid
user_id       uuid        -- owner, from the JWT
type          'shabbat_candles'
offset_min    90          -- 1h 30m
lat, lon, tz  saved location
enabled       true
next_fire_at  2026-10-02 16:34 local

How it fires: every minute the scheduler picks rows with next_fire_at ≤ now, publishes notification.requested, then asks Calendar for next week's candle lighting and sets next_fire_at = that − 90 min. Change the offset or your location and next_fire_at is recalculated right away.

The Kafka message

// topic: notification.requested   key: userId
{
  "notificationId": "7f3c…",      // dedupe on retry
  "userId": "u_123",
  "title": "Shabbat in 1h 30m",
  "body": "Candle lighting at 18:04",
  "channels": ["push"],           // optional; default = user's prefs
  "source": "reminders",
  "requestedAt": "2026-10-02T13:34:00Z"
}

This goes in libs/kafka-contracts, which is empty today, so both services share one typed contract.

Keying by userId keeps one person's notifications in order. notificationId lets the Notification Service skip a message it already sent if Kafka delivers it twice.

The message says what to tell you, not where. That's why adding email later is only a change to the Notification Service.

Your exact location

expo-location gives GPS coordinates, and @hebcal/core calculates from latitude, longitude and time zone directly. The time zone also decides Israel vs. abroad (one day of Yom Tov or two). Candle lighting defaults to 18 minutes before sunset and becomes a setting later (Jerusalem uses 40).

Needs HTTPS in the browser. Phone browsers only allow GPS on HTTPS. The web app is plain HTTP on :8081 today, so we add tailscale serve (a real certificate for your *.ts.net name). The native app doesn't need this.

Reminders will need your location saved on the server, since they fire while the app is closed. That's stored with the reminder in phase 2, not in phase 1.

Build order

Phase 1 · Shabbat + Calendar tab
  1. Calendar Service: apps/calendar with /calendar/shabbat, and @hebcal/core behind ICalendarCalculator. Tests against known dates and places.
  2. Gateway calendar-proxy: same shape as auth-proxy, rate-limited.
  3. Devops: a compose entry with no published port; HTTPS through tailscale serve.
  4. Home (H1): location permission, locationSlice, calendarSlice, times and countdown under the clock, last result cached.
  5. Calendar tab (C1): /calendar/month, the grid with both dates, and the day card.
Phase 2 · Reminders + notifications
  1. Kafka contract: notification.requested in libs/kafka-contracts.
  2. Notification Service: the Kafka consumer, device registration, and the Expo push adapter.
  3. Reminders Service: Postgres, CRUD, the scheduler, and publishing to Kafka.
  4. Frontend: expo-notifications, the bell button and offset sheet on the Home card, remindersSlice.
